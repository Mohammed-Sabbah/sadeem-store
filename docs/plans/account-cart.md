# خطة سلة الضيف وسلة الحساب

الحالة: منفذة محليًا بعد إذن صاحب المشروع. نتائج التحقق في سجل التنفيذ.
التاريخ: 2026-11-11.
مرجع القرارات: [ADR 0015](../adr/0015-guest-and-account-cart-storage.md).

## الهدف وحدود العمل

إصلاح دورة حياة السلة مع استخدام التخزين المحلي للضيف فقط، وحفظ سلة الحساب على السيرفر. يُسمح ببقاء مصدر نقل محلي معلّق يخص حسابًا محددًا إلى أن يؤكد السيرفر استلامه؛ لا يُستخدم المصدر لتخزين تعديلات الحساب.

البساطة وتقليل تغييرات الباك إند قيدان أساسيان. تُستخدم Express وMongoose وأنماط المصادقة والتحقق والاستجابة الموجودة. لا حاجة إلى مكتبات تشغيل جديدة أو WebSocket أو طابور مزامنة أو حفظ سلة الحساب للعمل دون اتصال أو إعادة هيكلة نظام الطلبات والمحفظة.

لا تُمس التعديلات الحالية غير المرتبطة بالسلة في واجهة الموقع. رسم التوصيل المؤقت 10 شيكل معتمد أصلًا في ADR 0014 والباك إند؛ تحديث تعارض التوثيق القديم معه مسألة توثيق، وليس إعادة تصميم التسعير ضمن هذه المهمة.

## السلوك المتفق عليه

| الحالة | النتيجة |
| --- | --- |
| زائر لم يسجل الدخول | سلة محلية، مع حماية القراءة والكتابة من أخطاء التخزين |
| استعادة الجلسة عند فتح الموقع | انتظار نتيجة المصادقة قبل اختيار سلة الضيف أو الحساب |
| الدخول أو إنشاء حساب | نقل اختيارات الضيف ودمجها في الحساب مرة واحدة |
| فشل النقل أو ضياع رد نجاحه | بقاء المصدر المعلّق وإعادة الطلب بنفس معرّف النقل دون مضاعفة الكميات |
| الخروج أو انتهاء الجلسة | إخفاء سلة الحساب فورًا، والاحتفاظ بها على السيرفر، وإظهار ضيف بسلة فارغة |
| تبديل الحساب | تحميل سلة الحساب الجديد وتجاهل ردود الحساب السابق |
| نقص المخزون أو توقف الصنف | إبقاء السطر مع السبب ومنع الشراء حتى المعالجة |
| تغير السعر | عرض السعر الحالي مع تنبيه؛ إعادة التحقق عند الشراء |
| تعديل على نسخة قديمة | رفض الكتابة المتعارضة وإرجاع السلة الحالية ليعيد الزبون التعديل |
| نجاح الطلب | استهلاك الكميات المشتراة فقط مع حفظ الإضافات الأخرى |
| فشل الطلب | السلة لا تتغير بسبب محاولة الشراء |

## المرحلة 1: عقد البيانات والاختبارات الأساسية

تُثبت أمثلة القبول أدناه قبل بناء الربط. الهوية الأساسية لسطر قابل للشراء هي `variantId`، بما يتوافق مع الطلبات الحالية. الخيارات المختلفة لا تُدمج. لا يُخمن متغير منتج قديم اعتمادًا على عنوانه أو أول خيار متاح؛ يبقى السطر الذي لا يمكن ربطه بخيار موثوق ظاهرًا للمستخدم لإعادة اختياره.

تُقبل الكميات الصحيحة المحدودة فقط، ويُستخدم `Number.isFinite` عند قراءة الأرقام القديمة. لا يُنشأ سعر صفر أو توثيق متجر أو مخزون متاح بوصفه بديلًا عن بيانات غير صالحة. تُعاد قراءة السعر والتوفر من الكتالوج، ولا يُوثق بسعر العميل.

## المرحلة 2: الحد الضروري في الباك إند

إضافة وحدة سلة صغيرة وفق نمط المشروع: نموذج، خدمة، متحكم، مسارات، والتحقق من الطلبات، ثم تسجيلها في `backend/app.js`.

- وثيقة واحدة لكل مستخدم مع فهرس فريد على `userId`، وعناصر السلة ورقم مراجعة `revision` يزيد مع كل تعديل.
- حفظ معرّفات الأصناف والكميات، والحد الأدنى اللازم لعرض سطر حذف من الكتالوج. بيانات العرض القديمة لا تصبح مرجع السعر أو التوفر.
- هوية المالك تأتي دائمًا من الجلسة؛ لا يقبل API اختيار مالك آخر في جسم الطلب.
- عمليات كتابة ذرية تفحص رقم المراجعة، وتعيد `409` مع السلة الحالية عند التعارض.

العقد المقترح يحصر المسارات في ثلاث عمليات:

| العملية | المسؤولية |
| --- | --- |
| `GET /api/cart` | إعادة السلة، المراجعة، والأسعار والتوفر الحاليين |
| `PATCH /api/cart` | إضافة أو تعيين كمية أو حذف أو إفراغ، مع `revision` ومعرّف للعملية |
| `POST /api/cart/import` | دمج مصدر قديم أو سلة ضيف باستخدام معرّف نقل ثابت |

تُحفظ نتيجة معالجة معرّف النقل/العملية مع التعديل نفسه، حتى لا يؤدي فقد الرد ثم تكرار الطلب إلى زيادة أخرى. تبقى إيصالات النقل صالحة بعد إفراغ السلة والشراء، ولا تُحذف بطريقة تسمح بإعادة استيراد مصدر قديم سبق استهلاكه. تُستعمل معاملات MongoDB الموجودة عند الحاجة، دون بناء خدمة مزامنة مستقلة.

الحدود المقترحة تتبع حدود الطلب الحالي: حتى 50 سطرًا وكميات حتى 1000 للوحدة. إذا تجاوز دمج المصدر الحدود، تُرفض العملية برسالة واضحة مع الاحتفاظ بالمصدر؛ لا تُحذف أصناف أو تُقص الكميات بصمت. تجاوز المخزون الفعلي يبقى تنبيه توفر، وليس سببًا لإسقاط اختيارات محفوظة.

## المرحلة 3: واجهة السلة ودورة المصادقة

إضافة خدمة سلة ضمن `frontend/features/cart` باستخدام عميل API الموجود، وجعل `CartContext` مسؤولًا عن التنسيق فقط. تُفصل قراءة بيانات الضيف وتنظيفها وعمليات نقلها في وظائف صغيرة قابلة للفحص.

- انتظار `AuthContext.isLoading` قبل تهيئة السلة؛ فشل جلب سلة الحساب يُعرض كفشل تحميل وليس كسلة فارغة مؤكدة.
- حالات واضحة: تحميل، جاهزة، حفظ، فشل، نقل معلّق. تُحجب إجراءات الشراء أثناء التحميل والنقل غير المحسوم.
- تعديل الحساب ينتظر تأكيد السيرفر. عند الفشل يبقى آخر وضع مؤكد مع إعادة محاولة؛ لا يوجد بديل محلي للحساب.
- عند الخروج أو التبديل، تُمسح بيانات العرض الخاصة بالحساب السابق وتُلغى أو تُتجاهل طلباته المتأخرة، باستخدام هوية الحساب ودورة الطلب.
- تحديث السلة عند دخول صفحتها أو العودة للنافذة وبعد الحفظ. تعارض المراجعة يُظهر تنبيهًا ويحدث السلة؛ لا يعاد تطبيق تعديل قديم تلقائيًا.
- تحديث مستهلكي دوال السلة في بطاقة المنتج وصفحة المنتج والسلة والدفع حتى تعرض نجاح الإضافة بعد تأكيد الحفظ أو تعرض الخطأ. مراجعة جميع الاستدعاءات قبل تغيير أنواع الدوال إلى دوال غير متزامنة.

## المرحلة 4: نقل الضيف والسلال القديمة

تُجهز حزمة نقل ثابتة بمعرّف واحد وحساب مستهدف قبل إرسالها. يُفصل المصدر المعلّق عن سلة الضيف النشطة؛ يمكن أن تبقى حزمة للحساب A أثناء استخدام الضيف أو الحساب B دون كشفها أو نقلها إليهما.

- قراءة `sadeem_cart_guest` بوصفه سلة الضيف الحالية.
- نقل `sadeem_cart_<userId>` فقط عند دخول الحساب المطابق.
- معالجة `sadeem_cart` بوصفه مصدر ضيف قديمًا، مرة واحدة.
- استخدام سجل محلي للنقل يربط المصادر ومعرّفها بالمالك قبل الطلب، لتكرار المحاولة بنفس المعرّف حتى بعد تحديث الصفحة أو تكرار effects.
- حذف المصدر بعد نجاح السيرفر فقط. إذا فشل حذفه محليًا، تمنع إيصالات السيرفر تكرار الدمج.
- حماية كل عمليات التخزين. إذا تعذر تثبيت بيانات نقل قابلة لإعادة المحاولة، تبقى المصادر ويُعرض تعذر النقل؛ لا يُرسل استيراد قد يتكرر بمعرّفات جديدة.
- عدم حذف الحزم المعلّقة في `logout` أو `clearCart`؛ انتهاء الطلب لا يعيد استيراد مصادر سبق نقلها.
- الأسطر القديمة غير القابلة للربط بخيار موثوق تبقى للمراجعة، مع بيان واضح لما لم يُنقل. لا يُعلن اكتمال نقل مصدر ولا يُحذف بينما يحتوي اختيارات لم تُحسم.

## المرحلة 5: الربط المحدود مع الطلبات

خدمة `backend/services/order.service.js` تستخدم بالفعل معاملة لإنشاء الطلب وخصم المحفظة والمخزون. يُضاف استهلاك الكميات المشتراة إلى نفس المعاملة، بدل طلب منفصل يمسح السلة بعد نجاح الدفع.

- إرسال مراجعة السلة مع طلب الشراء، وتحديث allowlist في `backend/schemas/orderSchema.js` ونوع الطلب في خدمة الواجهة والمتحكم بحسب الحاجة.
- التحقق من مراجعة السلة والكميات داخل المعاملة، ومن السعر والمخزون عبر المسار القائم. إذا تغيرت السلة قبل اعتماد الطلب، يرجع تعارض وتُعرض النسخة الحالية دون إنشاء طلب أو خصم رصيد.
- عند النجاح تُطرح الكميات المشتراة فقط، ولا تُمسح وثيقة السلة أو إيصالات النقل. الإضافات التي تسبق الطلب تسبب تحديثًا وإعادة تأكيد عند التعارض؛ الإضافات التي تليه تبقى. الكتابات المتزامنة تُحل ذريًا أو بتعارض، لا بكتابة نسخة قديمة فوق الجديدة.
- إذا تغير السعر عن آخر عرض مؤكد، يُطلب تأكيد الإجمالي الحالي قبل الدفع. فحص المخزون والتسعير الحالي لا يُستبدل ببيانات السلة.
- الواجهة تسترجع السلة المؤكدة بعد النجاح، وتزيل استعمال `clearCart()` المحلي من هذا المسار.
- فشل تحديث الواجهة بعد نجاح الطلب لا يُعرض كفشل شراء ولا يعيد إرسال طلب مالي تلقائيًا. تُعرض نتيجة الطلب المؤكدة مع إعادة جلب السلة.

## ترتيب التنفيذ والمراجعة

1. تثبيت عقد السلة وحالات القبول والحدود.
2. بناء وحدة الباك إند وفحوص الملكية والتعارض وعدم تكرار النقل.
3. ربط الواجهة والمصادقة والضيف، ثم النقل القديم.
4. ربط استهلاك السلة بمعاملة الطلب القائمة.
5. مراجعة الفرق واختبار الحالات أدناه، ثم تجربة يدوية لحسابين وضيف وجهازين.

كل مرحلة تنتج فرقًا قابلًا للمراجعة، وتُختبر قبل الانتقال لما يعتمد عليها. لا يُنشر ربط واجهة يحتاج API غير منشور؛ يُنشر دعم السيرفر أولًا أو يُنشر التغيير معًا. لا يُحذف التخزين القديم جماعيًا.

## اختبارات القبول

| الاختبار | معيار النجاح |
| --- | --- |
| ضيف ثم تسجيل حساب جديد | تنتقل الاختيارات وتُزال المصادر بعد تأكيد السيرفر |
| دخول حساب بسلة قائمة | جمع نفس الخيار وفصل الخيارات المختلفة |
| إعادة الطلب بعد ضياع الرد | لا تتضاعف الكمية، بما فيها إعادة المحاولة بعد شراء الأصناف |
| إعادة effects في Strict Mode | لا تضيع المصادر ولا يتكرر النقل |
| خروج أو انتهاء جلسة ثم دخول حساب آخر | لا تظهر بيانات الحساب الأول أو ردوده المتأخرة |
| فشل النقل ثم خروج وعودة | تبقى الحزمة للمالك الأصلي ويبدأ الضيف بسلة فارغة |
| سلة حساب قديمة على جهاز | لا تُرحّل إلا للحساب المطابق ولا تُحذف قبل النجاح |
| تخزين ممنوع أو ممتلئ وJSON تالف | لا تنهار الواجهة ولا يُحذف مصدر صالح قبل حفظه |
| سعر أو كمية غير منتهية أو هوية خيار ناقصة | لا تنتج مجاميع تالفة أو طلب شراء غير صالح |
| تغير سعر أو توقف متجر أو حذف خيار | يظهر السبب ويُطلب التصحيح أو التأكيد قبل الدفع |
| نقص المخزون | الاحتفاظ بالطلب الأصلي وتنبيه ومنع الشراء حتى التصحيح |
| تعديلان من جهازين | أحد التعديلين المتعارضين يُرفض ويُعرض الوضع الحالي |
| شراء مع إضافات متزامنة | لا تفقد الإضافات؛ تعارض آمن أو بقاء الإضافات بعد النجاح |
| فشل خصم أو إنشاء الطلب | تراجع المعاملة دون استهلاك أصناف السلة |
| حساب يحاول قراءة أو تعديل سلة غيره | الوصول مرفوض ولا يتغير شيء |

تُستخدم فحوص Node الموجودة للمنطق المستقل، وفحوص تكامل على MongoDB يدعم المعاملات للحالات الذرية. يضاف الحد الأدنى من أدوات الفحص إذا احتاجت فحوص التكامل ذلك، بعد توضيح السبب. تُشغل فحوص TypeScript وlint على الملفات المعدلة، ثم build الواجهة المناسب. تعثر بيئة الاختبار يُذكر صراحة ولا يُستعاض عنه بادعاء تحقق المعاملات.

## شروط جودة الكود وآلية قبول التنفيذ

هذه الشروط ملزمة للتنفيذ والمراجعة. المهارات وسائل مساعدة، واستخدام `poteto-mode` أو أي مهارة أخرى لا يعوض إثبات الالتزام بها. لا تُستدعى حزمة أدوات أو مهارات كاملة تلقائيًا إن كانت تضيف تعقيدًا غير لازم للمهمة.

### البساطة وحدود المسؤولية

- اتباع أنماط المشروع الموجودة، وعدم إضافة مكتبات تشغيل أو طبقات عامة أو إعادة هيكلة ملفات غير مرتبطة بالسلة دون حاجة محددة موثقة.
- المتحكم يعالج HTTP، وخدمة السلة تملك قواعدها، والموديل يحدد التخزين. لا تتكرر قواعد الدمج والكميات بين المسارات والمتحكم والواجهة.
- `CartContext` ينسق حالة الواجهة والمصادقة؛ تنظيف التخزين والنقل وقواعد هوية السطر توضع في وظائف أو وحدات واضحة. لا يُستبدل الملف المتضخم بشبكة من أغلفة أحادية الاستخدام.
- أسماء تكشف المعنى، وحالات تمثل المالك والتحميل والحفظ والفشل بوضوح. لا تتكاثر أعلام boolean تسمح بحالات متناقضة. تُحذف المسارات الداخلية القديمة بعد نقل مستدعيها؛ يبقى توافق البيانات القديمة في وحدة النقل فقط.

### صحة الحدود والأخطاء

- التحقق من مدخلات API والتخزين المحلي عند دخولها، واستعمال أنواع صريحة في الواجهة و`unknown` للبيانات الخارجية غير المثبتة؛ لا يُضاف `any` أو تحويل قسري لإسكات مشكلة في العقد.
- استنتاج المالك من الجلسة، والتحقق من الصلاحيات على السيرفر، ومنع الاعتماد على السعر أو التوفر المرسل من العميل.
- لا تُحوّل أخطاء تحميل سلة الحساب إلى نجاح بسلة فارغة، ولا تُخفى أخطاء النقل أو الحفظ في `catch {}`. تمييز عدم وجود سلة عن فشل قراءتها ضروري.
- لا تستخدم القيم الافتراضية لإخفاء فقد بيانات تجارية: لا سعر صفر تلقائيًا ولا متجر موثق افتراضيًا. بيانات العرض البديلة تكون واضحة بوصفها غير معروفة.

### صحة الحالة والتزامن

- لكل سلة معروضة مالك محدد، ولا تُحفظ حالة قديمة تحت هوية جديدة. الردود المتأخرة لا تحدث حالة حساب آخر.
- لا تُعطّل قواعد hooks أو تعتمد effects على قيم قديمة لتجاوز دورة التحميل. يجب أن تكون إعادة تشغيل effects وإعادة الطلبات آمنة.
- فحص المراجعة وتعديل السلة وتسجيل نجاح النقل عمليات ذرية، وليس قراءة ثم كتابة دون شرط. اختبار متزامن يثبت منع فقد التعديلات وتكرار النقل.
- إنشاء الطلب واستهلاك كمياته يحدثان داخل المعاملة القائمة نفسها. لا يُضاف مسار مستقل بعد الدفع يمكن أن يمسح إضافات جديدة أو يفشل ويترك سلة مشتراة دون معالجة.

### بوابات التحقق والمراجعة

1. **قبل الإصلاح:** إثبات فقد السلة القديم باختبار سلوكي يفشل على السلوك المعيب وينجح بعد الإصلاح. فحوص القواعد الجديدة تستخدم نتائج المستخدم المرئية، دون نسخ منطق التنفيذ داخل الاختبار.
2. **لكل مرحلة:** تشغيل فحوصها ومراجعة فرقها قبل بناء ما يعتمد عليها. لا تكفي mocks لإثبات ذرية MongoDB أو تراجع معاملة الدفع؛ يلزم فحص تكامل حقيقي.
3. **فحوص ثابتة:** نجاح TypeScript وlint المناسب وbuild، دون إضافة تعطيلات قواعد أو `@ts-ignore` لإخفاء أخطاء جديدة. الأعطال السابقة تُفصل بالأدلة عن الأعطال الناتجة عن التغيير.
4. **مراجعة نهائية:** مراجعة صحة اللوجيك والأمان ونظافة الكود، بالإضافة إلى أثر تغيير دوال السلة على جميع مستدعيها. لا تبقى مشكلة مفتوحة تسبب فقد بيانات أو خلط حسابات أو تكرار نقل أو أثرًا ماليًا غير صحيح.
5. **تسليم قابل للتحقق:** بيان الملفات المعدلة، سبب التغيير، أوامر الفحص ونتائجها، وأي حالة لم تختبر. لا يُعلن اكتمال متطلب لم يتحقق فعليًا.

التعليقات تشرح سبب قرار غير بديهي، ولا تسرد ما يظهر من الكود. لا يوجد حد اعتباطي لعدد الأسطر أو الملفات؛ معيار النظافة هو وضوح المسؤولية وسهولة تتبع العملية وتناسب حجم التغيير مع الحاجة.

## شرط الاكتمال

اجتياز اختبارات القبول، وعدم كتابة سلة الحساب العادية إلى التخزين المحلي، وعدم فقد اختيارات الضيف أو مضاعفة نقلها، وعدم خلط حسابين، وعدم تغيير منطق الدفع خارج التكامل اللازم لاستهلاك السلة. تُحدّث الوثائق بالنتيجة الفعلية عند التنفيذ.

أجاز صاحب المشروع تنفيذ هذه الخطة باستخدام `implement` و`poteto-mode` بعد مراجعتها. تفاصيل التنفيذ والمراجعة والفحوص في [سجل التنفيذ](./account-cart-run.md).
